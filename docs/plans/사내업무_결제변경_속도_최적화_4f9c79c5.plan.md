# 사내업무·결제변경 속도 최적화 (지속형 플랜)

> 문서 성격: **리빙 문서**. 스키마·비즈니스 로직 변경 없이 순수 캐시/렌더/네트워크 최적화만 축적한다.  
> 대상 화면: 사내업무판(`render_internal_work`) 및 결제변경 검증 흐름(`_render_payment_change_verify_entry`, `_render_payment_change_verify_panel`).  
> 관련 문서: 전역 성능은 [`docs/PERFORMANCE_AUDIT.md`](docs/PERFORMANCE_AUDIT.md) 유지. 본 문서는 "사내업무 + 결제변경" 세로 슬라이스에 한정.

## 1. 관측된 병목 (읽기 전용 조사 결과)

### 1.1 st.expander body 상시 실행
Streamlit 1.54에서 `st.expander` 는 접혀 있어도 내부 코드가 매 rerun 실행된다. 사내업무판에는 접힌 상세 카드가 다수 존재하며, 각 카드 안에 `_render_task_detail` → `_render_payment_change_verify_panel` 이 그대로 돈다.

- 근거: [`app.py:31224`](app.py) `with st.expander("📋 자세히 보기 …", expanded=_auto_expand):` 내부에서 무조건 `_render_task_detail(...)` 호출.

### 1.2 태스크당 무캐시 Supabase 쿼리 2건 (PCR 여부 판별)
[`task_board.py:1328-1352`](task_board.py) `load_payment_change_meta`, `load_payment_verify_state` 는 `@st.cache_data` 미적용. 카드가 20개면 rerun 당 40회 라운드트립.

### 1.3 PCR 검증 컨텍스트의 N+1 무캐시 쿼리
[`app.py:7370-7429`](app.py) `_pcr_build_verify_context` 내부에서 원본 결제 + 신규 결제 라인 각각에 대해
- `_pcr_load_payment_date(...)` 1회 ([`app.py:7347`](app.py), 무캐시)
- `_pcr_check_external_verification(...)` 최대 2회 ([`app.py:7257`](app.py), 무캐시)
- `_pcr_load_new_payment_ids_from_activity(...)` 1회 ([`app.py:7303`](app.py), 무캐시)

결제 라인이 3개면 PCR 카드당 **10–13회** 무캐시 쿼리.

### 1.4 결제변경 이력 조회 무캐시
[`app.py:7178`](app.py) `_load_latest_payment_history_for_pcr` — rerun 마다 재조회. `_pcr_display_meta_from_history` 가 매번 호출.

### 1.5 목록 보강 로더 무캐시
[`task_board.py:262`](task_board.py) `load_my_assigned_tasks`, [`task_board.py:1354`](task_board.py) `load_pending_payment_verifications` 는 `render_internal_work` 진입 시 반드시 호출되지만 캐시 없음.

### 1.6 결제변경 입력 폼이 페이지 전체 rerun 유발
[`app.py:30390`](app.py) `_render_payment_change_verify_entry` 는 `st.form` 이 아니라 `st.container(border=True)` 위에 개별 위젯을 두어, 입력마다 사내업무판 전체가 rerun 된다. 이미 클라이언트 사이드 콤마 포맷은 붙였지만 selectbox·checkbox 조작은 여전히 서버 왕복.

### 1.7 `clear_task_caches()` 광범위 무효화
[`task_board.py:408-418`](task_board.py) 는 8개 캐시를 일괄 `.clear()`. 댓글 1건 저장에도 알림·첨부·활동 캐시까지 콜드로 전환.

### 1.8 money-input JS iframe 반복 삽입
[`app.py:_inject_money_input_live_format`] 는 `components.html(..., height=0)` 로 매 rerun 마다 iframe 을 재삽입한다. MutationObserver 도 매번 새로 생성된다.

### 1.9 첨부 이미지 인라인 렌더 시 Storage GET 재발
[`app.py:29958`](app.py) `_render_attachment_inline` 은 `_fetch_attachment_bytes_cached(600s)` 를 쓰지만, 태스크 상세가 접혀 있어도 실행되므로 태스크당 다중 첨부에 대해 캐시 miss 시 대량 다운로드 가능.

## 2. 조치 로드맵

각 조치는 **스키마 변경 없음**, **비즈니스 로직 불변**을 원칙으로 한다.

### Phase A — 즉시 (핫스팟 캐시 부착)

- **A1. PCR 판별용 무캐시 쿼리에 TTL 캐시 부착**  
  [`task_board.py:1328`](task_board.py) `load_payment_change_meta`, [`task_board.py:1340`](task_board.py) `load_payment_verify_state` 각각 `@st.cache_data(ttl=30, show_spinner=False)` 부착. `clear_task_caches()` 에 새 항목 추가.

- **A2. 결제변경 이력·결제일자·외부검증 캐시화**  
  [`app.py:7178`](app.py) `_load_latest_payment_history_for_pcr`, [`app.py:7347`](app.py) `_pcr_load_payment_date`, [`app.py:7257`](app.py) `_pcr_check_external_verification`, [`app.py:7303`](app.py) `_pcr_load_new_payment_ids_from_activity` 에 `@st.cache_data(ttl=30~60)`. 결제/외부매칭 CRUD 지점(`_insert_payment_supabase` 등)에서 해당 캐시 `.clear()`.

- **A3. 담당/미결 리스트 캐시**  
  [`task_board.py:262`](task_board.py) `load_my_assigned_tasks`, [`task_board.py:1354`](task_board.py) `load_pending_payment_verifications` 에 `@st.cache_data(ttl=30)`. `clear_task_caches()` 에 편입.

### Phase B — 렌더 지연 (expander body gating)

- **B1. 상세 렌더 lazy execution**  
  [`app.py:31224`](app.py) 에서 상세 렌더를 `st.session_state[f"task_open_{tid}"]` 플래그로 게이트. 최초 클릭 시에만 `_render_task_detail(...)` 실행, 이후 접히면 skip. `_auto_expand` (알림 딥링크)일 때는 강제 True. 이렇게 하면 카드 20개 중 열려있는 1–2개만 상세를 실행.

  ```python
  key = f"task_open_{tid}"
  st.session_state.setdefault(key, bool(_auto_expand))
  # expander 대신 커스텀 토글 버튼으로 open/close 관리하거나
  # expander + on_change (Streamlit ≥1.36) 사용 (1.54 에서 지원)
  ```

- **B2. `_render_payment_change_verify_panel` 초기 short-circuit**  
  [`app.py:31266`](app.py) 는 `task.get("task_type") == PAYMENT_CHANGE_TASK_TYPE` 인 경우에만 진입하도록 조기 리턴. 현재는 모든 태스크에서 `load_payment_change_meta` 호출 → 캐시 도입해도 무조건 1쿼리. `task["task_type"]` 이 이미 로드되어 있으니 그것만 검사.

### Phase C — 배치 프리로드

- **C1. PCR meta 벌크 로드**  
  `render_internal_work` 에서 태스크 목록 확정 후 PCR 태스크 id 만 뽑아 1회 IN 쿼리:
  ```
  app_payment_change_requests.select("*").in_("task_id", pcr_ids)
  ```
  결과를 dict 로 `_render_task_card` → `_render_task_detail` → panel 까지 파라미터로 전달. 개별 `load_payment_change_meta` 호출 제거.

- **C2. 외부검증 벌크 로드**  
  [`_pcr_check_external_verification`] 을 payment_id 다중 IN 쿼리로 감싸는 헬퍼 `_pcr_bulk_verify(db_filename, pids)` 신설. panel 진입 시 한 번만 호출 → dict 로 조회.

- **C3. 결제일자 벌크 로드**  
  마찬가지로 `_pcr_bulk_payment_dates(db_filename, pids)` 로 통합.

### Phase D — rerun 격리 (`@st.fragment`)

Streamlit 1.32+ 의 `@st.fragment` 를 사용 (1.54 에서 안정). 스키마/로직 변경 없이 rerun 범위만 축소.

- **D1. `_render_payment_change_verify_entry` 를 fragment 로**  
  [`app.py:30390`](app.py). 결제 라인 추가·selectbox 조작 시 사내업무 전체가 아니라 이 폼만 rerun. 파일 첨부 업로드는 여전히 상위 st.rerun() 로 전체 갱신 (완료 후 목록 갱신 필요).

- **D2. `_render_payment_change_verify_panel` 을 fragment 로**  
  검증완료/반려 버튼 클릭도 fragment 안에서 처리. 완료 시에만 `clear_task_caches()` + 상위 rerun trigger.

- **D3. 알림 패널을 fragment 로**  
  [`app.py:29367-29399`](app.py). "읽음 처리" 클릭이 전체 rerun 을 유발하는 문제 완화.

### Phase E — 세분화된 캐시 무효화

- **E1. `clear_task_caches()` 분리**  
  [`task_board.py:408`](task_board.py) 를 3개로 쪼갠다:
  - `clear_task_list_caches()` — `load_tasks_cached`, `load_my_confidential_tasks_cached`, `load_task_assignees_cached`, PCR 목록 캐시
  - `clear_task_detail_caches()` — 댓글·첨부·활동 (특정 task_id 만)
  - `clear_notification_caches()` — 알림 관련만
  
  각 CRUD 지점에서 필요한 것만 호출. 예: 댓글 추가 → `clear_task_detail_caches(tid)` 만.

### Phase F — 클라이언트/네트워크 잔가지

- **F1. money-input JS 세션 1회 마운트**  
  `st.session_state["_money_js_mounted"]` 로 이 rerun 에서 아직 안 붙였을 때만 `components.html(...)` 호출. iframe 재삽입 비용 제거.

- **F2. 첨부 지연 로딩**  
  Phase B1 이 적용되면 접힌 태스크의 `_render_attachment_inline` 자체가 실행되지 않아 자연 해소. 별도 조치 불필요.

- **F3. 태스크 카드 담당자 표시명 사전 조회**  
  `_uname_to_display` 가 dict 조회지만 매 카드에서 반복. `render_internal_work` 진입 시 1회만 dict 를 로컬 변수로 잡고 넘기기.

## 3. 우선순위 & 예상 효과

- Phase A → 사내업무 목록 rerun 당 **DB 라운드트립 40+회 → 0회 (캐시 hit)**. 체감 1–3초 단축.
- Phase B → 접혀 있는 태스크의 상세 코드가 실행되지 않아 rerun 당 **PCR 컨텍스트 조회 대부분 skip**. 20개 카드 기준 추가 1–2초 단축.
- Phase C → 캐시 miss 시에도 PCR 관련 쿼리를 **개수와 무관하게 3회 이내**로 상한. 초기 진입 콜드 스타트 개선.
- Phase D → 결제변경 폼 입력 시 **전체 rerun 제거**. 사용자가 가장 느리다고 느끼는 지점 직격.
- Phase E → 댓글 1건 저장 후 화면 재진입 시 리스트/알림 캐시 유지 → 0.5–1초 단축.
- Phase F → 잔여 iframe/렌더 노이즈 정리.

## 4. 측정 방법 (Phase 별 검증)

각 Phase 후 아래를 로컬에서 수동 측정:

1. 사내업무 진입 (열려있는 태스크 15개, PCR 3개 포함) — 첫 렌더 시간
2. 태스크 카드 하나 열고 아무 텍스트 필드 타이핑 — 응답 지연
3. 결제변경 폼 열고 결제 라인 3개 입력 — 라인 추가 시 지연
4. 검증완료 버튼 클릭 후 다음 rerun 시간

간단한 `time.perf_counter()` 로그를 아래 지점에 임시 삽입 (배포 전 제거):
- `render_internal_work` 시작·종료
- `_render_payment_change_verify_panel` 시작·종료
- `_pcr_build_verify_context` 시작·종료

## 7. 이번 승인 시 즉시 실행 범위

플랜 승인 시 **Phase A + Phase B + Phase D-1** 만 우선 구현한다. 이유:
- A/B: 리스크 매우 낮음 (캐시 부착, 조기 리턴, expander gating). 즉시 효과 큼.
- D-1: 결제변경 입력 폼은 사용자가 가장 느리다고 지목한 지점이라 우선 반영.

Phase C/D-2/D-3/E/F 는 별도 승인 사이클로 진행 (본 문서에 항목만 유지).
